# Фоновые задачи

TaskIQ использует Redis Streams и очередь `bgitu:tasks`. Воркер подтверждает
сообщение после сохранения результата. Результаты хранятся 24 часа
(`BGITU__TASKIQ__RESULT_TTL_SECONDS`). Новая consumer group читает поток с начала,
поэтому задача, отправленная до запуска первого воркера, не пропускается.

В `tasks.sessions` зарегистрирована очистка сессий: ежедневно в 03:10 UTC.
Удаляются истёкшие сессии и сессии, отозванные более семи дней назад, в одной
транзакции. Повторное выполнение безопасно. Ошибка БД не маскируется успешным
результатом. Пул asyncpg живёт в event loop воркера и закрывается при его остановке.

Команды запуска приведены в корневом README. Модуль `tasks.sessions` нужно
передавать и воркеру, и планировщику: без его импорта задачи не зарегистрируются.
Запускается ровно один планировщик; `--skip-first-run` исключает повторную отправку
задачи в текущую минуту при перезапуске.

## Обновление существующей установки

1. Остановить старые контейнеры `diplom_celery_beat` и `diplom_celery_worker`.
   Не запускать старый и новый планировщики одновременно.
2. В локальном `.env` заменить `BGITU__CELERY__BROKER_URL` и
   `BGITU__CELERY__RESULT_BACKEND` на соответствующие `BGITU__TASKIQ__*`.
   Старый параметр часового пояса удалить: расписание теперь явно фиксировано в UTC.
   В Compose адреса Redis уже заданы в общем окружении.
3. Выполнить `uv sync` для локального запуска или пересобрать Docker-образ.
4. Запустить сервисы `taskiq_worker` и `taskiq_scheduler`.

Старые сообщения Celery несовместимы с TaskIQ и автоматически не переносятся.
Единственная прежняя задача является периодической очисткой: следующий запуск
обработает оставшиеся истёкшие сессии. Не очищайте Redis целиком: он также хранит
кэш и состояние realtime. Схема БД для смены очереди не меняется.

Redis в текущем Compose не имеет постоянного тома: пересоздание контейнера
теряет очередь. Это допустимо для этой периодической идемпотентной очистки,
но требует отдельного решения перед добавлением задач, которые нельзя потерять.
Ошибки выполнения видны в логах воркера и результате TaskIQ; автоматического
повтора ошибок приложения нет. Неподтверждённые сообщения после аварии воркера
Redis Streams возвращает в обработку (стандартный интервал TaskIQ Redis: 10 минут).
